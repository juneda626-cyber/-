# FLUXIA Capital Intelligence

上場企業の資金需要、M&A・投資動向、IPO準備企業、および企業間シナジーを一元的に把握するための情報提供エンジンです。現在は **Phase 1 MVP** として、SQLiteに保存した財務値から資金需要スコアを計算し、APIと画面で確認できます。

## 現在できること／できないこと

現時点では、データ収集元を接続する前の**ローカルMVP**です。判定ロジック、API、詳細画面までを一貫して試せます。

| 項目 | 現在の状態 |
| --- | --- |
| ダッシュボードの表示 | API連携済み |
| 資金需要の緊急度フィルター | 利用可能 |
| 企業名・証券コードの画面内検索 | 利用可能 |
| 財務値のSQLite保存・スコア計算 | 利用可能 |
| 企業詳細・検知根拠 | 利用可能 |
| JSON API | 利用可能 |
| スクリーニング条件入力 | UIのみ |
| EDINET・TDnetからの自動収集 | 未接続 |
| EDINET実データによる財務分析 | 未実装 |
| 非上場企業の登録・マッチング | 未実装 |

初期状態の社名・数値はデモ用の架空データです。EDINET取得後は「実データ」ラベルを付けて区別しますが、スコアは調査優先度の参考情報であり、投資判断へ直接利用しないでください。

## EDINET実データ（対象：株式会社イー・ロジット）

今回の対象は、候補5社のうち株式会社イー・ロジット（証券コード9327、EDINETコードE36405）です。EDINET API v2の書類一覧APIから同社の直近XBRL対象書類を探し、書類取得APIのXBRL ZIPを解析します。実装は金融庁の[EDINET API関連資料](https://www.fsa.go.jp/search/20240328.html)および[EDINET](https://disclosure2.edinet-fsa.go.jp/)で公開されるAPI v2仕様に従っています。

### 1. APIキーを取得する

1. EDINETを開いて利用者登録・ログインを行います。
2. APIキー発行画面からキーを発行します。画面名はEDINET側の更新で変わる場合があるため、公式の「API仕様書」および画面案内も確認してください。
3. キーをチャット、ソースコード、`.env`、GitHubへ書かず、実行するターミナルだけに環境変数として設定します。

Windows PowerShellでは、同じPowerShellウィンドウ内で次を実行します。

```powershell
$env:EDINET_API_KEY = Read-Host "EDINET APIキー"
```

macOS/Linuxでは次のとおりです（シェル履歴へキーを残したくない場合）。

```bash
read -s EDINET_API_KEY && export EDINET_API_KEY
```

### 2. 取得して保存する

```powershell
python edinet.py --target e-logit --days 180
```

取得結果は`data/fluxia.db`の`edinet_filings`と`financial_observations`へ保存されます。各観測値には、書類ID、APIの出典URL、対象期間、XBRL単位、連結・単体区分、XBRL概念名、取得日時を保存します。現預金、営業CF、自己資本、総資産、短期借入金、1年内返済予定長期借入金、長期借入金、社債を抽出し、有利子負債は取得できた構成項目だけを合計します。取得できない値を0にはしません。

環境にAPIキーがない場合は、実行前に明確なエラーで停止します。本リポジトリにはキーも取得済みの実データもコミットしません。

### 3. WindowsのChromeで確認する

Codex環境の`localhost`ではなく、**リポジトリをダウンロードしたWindows PC上**で次を行います。

1. GitHubでこのPRをマージし、Windows PCでリポジトリを`git pull`（初回はClone）します。
2. PowerShellでリポジトリのフォルダーへ移動します。
3. 上記手順で`EDINET_API_KEY`を設定し、`python edinet.py --target e-logit --days 180`を実行します。
4. `python server.py`を実行したままにします。
5. 同じWindows PCのChromeで`http://127.0.0.1:4173`を開きます。
6. 一覧の緑色の「実データ」ラベルが付いたイー・ロジットを押し、数値、判定理由、不足項目、書類ID、期間、単位、区分、取得日時を確認します。

### 現時点の検証状況

この開発環境には`EDINET_API_KEY`が設定されておらず、外部通信もHTTP 403で遮断されたため、EDINETからの実ファイル取得および原本との数値照合は**未検証**です。XBRL ZIPの解析、SQLite保存、不足値を「判定不可」とする分析、APIへの受け渡しは自動テスト済みです。キーのあるネットワーク環境で上記コマンドを成功させるまでは、実データ取得済みとは扱わないでください。

## まずデモを使う

### 1. 起動する

外部パッケージは不要です。リポジトリ直下でAPIサーバーを起動してください。初回起動時に `data/fluxia.db` が自動作成されます。

```bash
python3 server.py
```

ブラウザで `http://localhost:4173` を開きます。

サーバーを停止するときは、起動したターミナルで `Ctrl+C` を押します。

### APIを使う

```bash
curl http://localhost:4173/api/health
curl 'http://localhost:4173/api/signals?urgency=high&q=バイオ'
curl http://localhost:4173/api/companies/4589
```

`GET /api/signals` はスコア降順の企業一覧を返し、`urgency=high|mid|low` と `q=検索語` を指定できます。`GET /api/companies/{証券コード}` は算出根拠を含む企業詳細を返します。

### テストする

```bash
python3 -m unittest discover -s tests -v
```

### 2. 操作を試す

1. 「資金需要シグナル」の `緊急度 高`、`中`、`低` を押して企業を絞り込みます。
2. 上部の検索欄へ会社名、証券コード、キーワードを入力します。`Ctrl+K`（macOSでは `⌘K`）でも検索欄へ移動できます。
3. 企業行を押し、算出スコア、財務値、検知根拠を確認します。
4. 右上の「スクリーニング」から、市場・探索テーマ・時価総額上限を入力します。
5. 左メニューで、将来提供するM&A動向、マッチング、レポートなどの画面構成を確認します。

## 主な機能

- 財務データに基づく資金需要シグナルと緊急度フィルター
- 適時開示・決算資料から抽出したM&A／新規事業／投資動向
- 上場企業と非上場企業のAIマッチスコア表示
- 横断検索、スクリーニング条件作成、ウォッチリスト導線
- デスクトップとモバイルに対応したレスポンシブUI

## 実際に使えるサービスにするための次のステップ

最初から全機能を作らず、次の3段階で進めることを推奨します。

### Phase 1 — 上場企業の資金需要検知（最初のMVP）

まず①と②に絞り、投資家が毎日確認できるプロダクトを作ります。

1. **対象を決める** — 例として東証グロース／スタンダード、時価総額100億円以下に限定します。
2. **データを収集する** — EDINETの有価証券報告書・四半期報告書、TDnetの適時開示、取引所の銘柄情報を日次で取得します。
3. **財務指標を計算する** — 現預金、月次キャッシュバーン、現預金ランウェイ、営業CF、自己資本比率、有利子負債、継続企業の前提に関する注記を企業・決算期単位で保存します。
4. **シグナルを判定する** — 単一指標だけで断定せず、複数指標のルールと根拠を組み合わせてスコア化します。
5. **企業詳細を作る** — 株主構成、事業セグメント、役員、過去の資金調達、直近開示、算出根拠、原典リンクを表示します。
6. **アラートを届ける** — 新規シグナルとスコア変化をメールまたはSlackへ通知します。

最初の判定例です。

```text
対象月数             = 営業CFの対象期間（四半期=3、半期=6、通期=12など）
月次キャッシュバーン = max(0, -対象期間の営業CF / 対象月数)
現預金ランウェイ     = 現金及び現金同等物 / 月次キャッシュバーン

高リスク候補:
  ランウェイ < 6か月
  または、ランウェイ < 12か月 かつ 営業CF悪化 かつ 自己資本比率低下
```

これは「増資が必要」と断定するモデルではなく、調査優先度を決めるためのシグナルです。設備投資、前受金、借入枠、資産売却、季節性なども人が確認できる設計にします。

### Phase 2 — M&A・新規事業・投資意向の検知

③のため、適時開示、決算説明資料、中期経営計画、ニュースリリースから次の情報を抽出します。

- 買収、資本業務提携、CVC設立、新規事業、事業ポートフォリオ変更に関する記述
- 対象業界、技術テーマ、地域、想定投資額、検討時期
- 原文、資料名、公開日、URL、該当ページ

抽出結果には必ず原典と信頼度を付け、AIの要約だけでなく担当者が根拠を確認できるようにします。

### Phase 3 — 非上場企業データとマッチング

④の非上場企業情報は公開情報だけでは不足するため、企業自身または提携先から登録してもらう仕組みを作ります。

- 事業概要、顧客属性、売上レンジ、成長率、収益モデル
- 調達履歴、希望する資本政策、IPO準備状況、監査法人・主幹事の状況
- 希望する提携形態、売却意向、公開範囲、情報の更新日

そのうえで「事業テーマ」「顧客・販路」「保有技術」「地域」「投資予算」「希望条件」を用いて候補をランキングし、双方の承諾後に詳細情報を開示するワークフローへ発展させます。

## 推奨するシステム構成

```text
EDINET / TDnet / IRサイト / 企業入力
                │
                ▼
       収集ジョブ・文書保管
                │
                ▼
      正規化DB・検索インデックス
                │
       ┌────────┴────────┐
       ▼                 ▼
 財務シグナル計算     文書分類・情報抽出
       └────────┬────────┘
                ▼
          API・権限制御
                │
                ▼
  本ダッシュボード / 通知 / CSV出力
```

実装時には、以下を最低限分離します。

- **収集層** — API・Web公開資料の取得、再実行、重複排除、取得履歴
- **データ層** — 企業、証券、決算、株主、開示文書、イベント、非上場企業、マッチ候補
- **分析層** — 財務指標計算、ルール判定、文書抽出、マッチスコア、根拠保存
- **提供層** — 認証、検索、企業詳細、ウォッチリスト、アラート、監査ログ

## 最初の開発スプリントで決めること

以下の5点が決まれば、実データ版の実装に着手できます。

1. 最初の利用者は誰か（投資家、上場企業の経営企画、M&Aアドバイザーなど）
2. 対象市場と時価総額上限
3. 資金需要シグナルの判定条件と、許容する誤検知率
4. 最初に通知する手段（画面、メール、Slack）
5. 非上場企業データを誰が、どの契約・更新頻度で提供するか

MVPの完了条件は、例えば「対象企業を毎日自動更新し、根拠資料付きの資金需要候補を一覧・詳細・通知で確認できること」とします。その後、利用者の反応を見てM&A検知と非上場企業マッチングを追加します。
